我固定的模型與控制流程

狀態是 CPU 溫度、GPU 溫度與有效風扇比例 f；輸入是 PWM u。入口溫度與當下 CPU／GPU 負載是擾動。所有方法只見當下觀測，不提供未來負載。

Ci · dTi/dt = Pi − (Gi + kif) · (Ti − Tin)
τ · df/dt = u − f；RPM = RPMmax · f = 6000f

上式是我的數學化整理，參數是研究假設，沒有宣稱出自文獻的逐字公式或實機辨識。以下數值是名義模型設定；假設參數變體另列於完整設定。

研究定位：模型遷移到機箱的前置研究。我先建立機箱的簡化熱模型，作為原有數位孿生方法遷移到機箱場景的候選物理主模型。目前參數採假設值，後續將以量測資料辨識參數，再接入自己的稀疏感測校正、設備影響學習與殘差修正流程。現階段只涵蓋溫度子問題，尚未完成原本三因子方法的整套遷移。

這組參數實際用在哪裡：C、G、k、τ與最大RPM描述「CPU、GPU雙熱節點＋風扇延遲」的特性；本輪固定為假設值，沒有從實機資料辨識。模擬plant依此產生反應，作為固定風扇／PID／LQR／MPC比較的測試環境。MPC／LQR使用其名義模型的局部離散形式，PID的負載前饋也使用名義散熱關係。PID增益、LQR的Q/R、MPC的預測步數與權重則是另外設定的控制器參數。

Tin機箱入口空氣溫度°C兩節點共用的外部擾動，由情境給定，約30°C附近變動；與 Ti 相減得到溫差，1°C溫差等於1 K。
f有效風扇比例／正規化轉速狀態無因次，0–1模擬初始 f=0.5；不是PWM命令本身，會因風扇延遲逐步接近 u。
df/dt有效風扇比例的變化率s⁻¹由 (u−f)/τ 決定；u大於f時加速，小於f時減速。
τ風扇一階響應時間常數s20秒；固定u時，經過一個τ約完成63.2%的剩餘變化，並非瞬間到達命令值。
u控制器送出的PWM占空比命令無因次，0–1本輪允許 0.2–1（20%–100%）；每步變化最多 0.1，即10個百分點。
RPMmax假設最大風扇轉速rev/min（轉/分鐘）6000；是模型換算係數，尚未以實際風扇校準。
RPM由 f 換算的模型風扇轉速rev/min（轉/分鐘）RPM=6000f；例如f=0.5對應3000 RPM。這是線性假設，不代表真實PWM與RPM必然成正比。

9月中下旬，我把參數調教標準化

我9月中下旬把「調參」從找一組漂亮分數，改成任何人都能重做的流程：先分清楚哪些參數可以調，再固定資料切分與搜尋預算，鎖定參數後才讀取 validation／holdout，最後用同日期的 fixed PI 做比較。這樣才能知道改善來自方法，還是只是看過答案後再調整。

第一層

先分清楚哪些參數能調

我把物理／量測常數、動態模型、控制器參數和實驗設計分開。sample time、單位與致動器界限先固定，不能為了分數事後修改。

第二層

先校正，再鎖定後驗證

calibration 只用來辨識與搜尋；參數鎖定後，validation 和 holdout 各只讀取一次。沒有獨立資料就標記 NO_INDEPENDENT_VALIDATION。

第三層

用固定規則決定是否繼續

我預先固定粗網格、搜尋預算、IAE／ITAE、tie margin 與飽和檢查；不無限試到滿意，也不把持平硬說成勝出。

一句話：我現在不是問「哪組參數分數最高」，而是問「在沒有看 holdout 答案的前提下，鎖定的參數能不能讓預測操作後的溫度仍然準確」。

具體示範（使用我的 DigitalTwinModel）：我先把 8 顆感測器觀測送進模型，讓模型校正 `ac_main` 的有效功率與空間 residual；接著固定目標為 25°C／58% RH／500 lux，只比較 AC activation 35%、60%、85% 三個候選。模型預測的 zone temperature 分別是 27.509°C、26.559°C、25.609°C，comfort penalty 分別是 3.898、2.907、2.308，因此這次 dry run 排名第一的是 85%。真正介入時，才把 85% 送到 actuator，再用介入後實測溫度和 25.609°C 比較 MAE；這一步目前尚未有實體證據。
機箱模型版示範（示範計算，不是實測）：我把狀態固定為入口 30°C、CPU 72°C、負載功率 180 W，並先用一組待 calibration 的參數 C=12000 J/°C、G=8 W/°C、k_f=1.5 W/(°C·krpm)、5 分鐘 horizon。假設 PWM 40%／60%／80% 分別對應 3000／4500／6000 RPM，模型計算出的 5 分鐘後 CPU 溫度示範值為 63.38／61.01／58.65°C。這個例子展示的是「候選風扇操作 → 預測後續溫度」的格式；真正研究時，這些係數要由 calibration 資料辨識，再用 validation／holdout 的實測溫度計算 MAE。

我的模型流程架構：從資料到控制驗證

我把模型流程拆成六個可檢查的階段。每一階段都有固定輸入、輸出與證據狀態，避免把「模型提出動作」直接寫成「實體控制已有效」。目前這張架構圖是以桌機機箱為應用主軸，TCLab／BOPTEST 只提供可重現的動態模擬環境。

1. 資料契約同步入口溫度、CPU／GPU 溫度、負載功率、PWM、RPM 與取樣時間；先檢查單位、時間戳和缺值。
2. 狀態與特徵把當前溫度、負載與風扇狀態整理成模型輸入；固定 sample time、初始狀態與安全界限。
3. 熱模型辨識用 calibration 的階躍回應估計 C/G/k_f/τ_f/k_L，並記錄搜尋範圍、seed 與失敗原因。
4. 候選操作預測對每個 PWM／RPM 候選推演未來 horizon 的 CPU／GPU 溫度，計算超溫、追蹤與功耗 proxy。
5. 動作選擇在安全限制內依事前固定的 penalty、tie margin 與飽和規則選出操作；輸出的是模型推薦，不是已執行的介入。
6. 獨立驗證鎖定參數後只讀取 validation／holdout，將預測溫度與操作後實測溫度比較，再和 fixed PI／原廠策略比較。
