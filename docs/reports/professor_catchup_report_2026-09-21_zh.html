往下做時，我卡在幾個問題

估測準，是否就有控制上的價值？

我原本能比較估測誤差，但當我想往控溫或節能延伸時，就發現還缺少動態響應與介入證據。即使溫度估得準，我仍需要驗證改變控制動作後，環境究竟會怎麼反應。

環境條件化 PID 是否已有先例？

我查文獻後找到既有自動調參研究，例如 Fiducioso 等人（2019）的 contextual Bayesian optimization。因此，我需要進一步釐清自己的方法差異，並比較相同控制品質下的資料與試調成本；目前還沒有建立新穎性主張。

只維持固定設定值，是否已經足夠？

我也問自己：如果一般開關控制或 PI 就能維持固定目標，加入模型或神經網路的價值在哪裡？所以我需要先找出簡單策略的不足。目前這些 BOPTEST 實驗尚未驗證神經網路的效益。

資料與模擬能回答哪些應用問題？

我當時沒有找到能直接量測半導體環境調參工時的公開資料，因此先用 BOPTEST 做控制模擬。若要延伸到桌機機箱，我仍需要入口溫度、負載、PWM/RPM、功率與實機介入證據，才能評估溫度、效能與耗電。

依據：環境參數 PID 啟動條件與 候選應用及固定設定質疑。

我如何找到可以模擬環境的 API

當我發現 BMC／AAU 紀錄不足以驗證新控制動作時，我開始找能接收控制指令、回傳下一步環境狀態，而且可以重設、重複比較的模擬平台。

我的查找範圍從機箱溫控，擴展到精密環境的快速調適。我查了 APMonitor 的 TCLab 建模教材、IBPSA BOPTEST 官方介紹與案例頁、UCI SECOM，以及 OpenHumidistat 作者論文。當時我沒有取得可直接使用的 EUV／半導體環境調參資料，因此先選擇一般 HVAC 模擬來檢查方法。以下依我 9/8 留存的筆記整理；完整搜尋字串與逐次點閱時間沒有留存。

1. 我釐清需求我要觀察控制動作之後的環境反應，因此需要可互動的動態模型。
2. 我比較候選我查了 TCLab、BOPTEST、SECOM 與 OpenHumidistat，確認資料和控制介面。
3. 我選 BOPTEST它提供多種 HVAC 模型、天氣、控制點與 REST API，符合這輪比較需求。

候選來源 我為什麼查它 我最後怎麼選
TCLab／TCLabModel 我在建模教材中找到加熱輸入與溫度反應，適合用來做初步熱動態辨識。 我已完成 simulation smoke test。本地 `tclab==1.0.0` 的 `TCLabModel(synced=False)` 已通過 reset、輸入、時間推進與溫度回應；但仍不是硬體證據。
IBPSA BOPTEST／API 使用說明 我在官方介紹和 API 文件中確認，它有動態模型、天氣、量測／控制點、模擬步進與 KPI。 我選為主要模擬平台，因為我能重設案例，讓不同控制器在相同條件下比較。
UCI SECOM 它來自半導體製程，所以我查了是否能支援精密環境控制問題。 我排除為控制主資料，因為其中是製程特徵與 pass/fail，缺少我需要的具名設定值、PID 係數及連續控制動作。
OpenHumidistat 我從作者論文找到開源濕度控制實驗腔，想確認它能否成為實測平台。 我保留為硬體備案；這次尚未建立該裝置，也沒有取得現成的完整溫濕度雙變數模擬 API。
我選 BOPTEST 的關鍵理由：我可以讓控制器讀取量測、送出動作，再觀察環境往前演化的結果。這樣就能把固定 PI、自動辨識 PI、observer、smoothing 與 handover 放在相同模型、日期、warmup 與限制下比較。
我在 API 文件中確認了什麼？實驗最後怎麼執行？

我確認官方 API 的基本循環是：選案例取得 testid → 初始化與 warmup → 讀取量測／致動器名稱及單位 → 設定步長 → 提交動作並前進一步 → 取得新量測，反覆執行後讀取結果。這些介面可在 BOPTEST 官方 API 文件查到。

用途官方介面摘要
建立與重設案例POST /testcases/{name}/select；PUT /initialize/{testid}
檢查可觀測與可控制的量GET /measurements/{testid}、GET /inputs/{testid}
控制一步並取得環境反應PUT /step/{testid}；POST /advance/{testid}，送入指令及 override 啟用旗標
取回完整軌跡與官方指標PUT /results/{testid}、GET /kpi/{testid}

實際執行時，我採用固定的官方 v0.9.0 FMU（可執行的動態模型），透過 FMPy 直接呼叫 FMI 介面。我把起始 pilot 設為每步 60 秒、目標 22°C、每回合共用 24 小時 warmup，再用自訂程式計算 MAE 等指標。我尚未驗證這條路徑與官方 REST 服務或 KPI 完全等價；控制器也沒有沿用原空間估測網路的權重。

這週，我把參數調教標準化

我這週把「調參」從找一組漂亮分數，改成任何人都能重做的流程：先分清楚哪些參數可以調，再固定資料切分與搜尋預算，鎖定參數後才讀取 validation／holdout，最後用同日期的 fixed PI 做比較。這樣才能知道改善來自方法，還是只是看過答案後再調整。

第一層

先分清楚哪些參數能調

我把物理／量測常數、動態模型、控制器參數和實驗設計分開。sample time、單位與致動器界限先固定，不能為了分數事後修改。

第二層

先校正，再鎖定後驗證

calibration 只用來辨識與搜尋；參數鎖定後，validation 和 holdout 各只讀取一次。沒有獨立資料就標記 NO_INDEPENDENT_VALIDATION。

第三層

用固定規則決定是否繼續

我預先固定粗網格、搜尋預算、IAE／ITAE、tie margin 與飽和檢查；不無限試到滿意，也不把持平硬說成勝出。

一句話：我現在不是問「哪組參數分數最高」，而是問「在沒有看 holdout 答案的前提下，鎖定的參數能不能讓預測操作後的溫度仍然準確」。

具體示範（使用我的 DigitalTwinModel）：我先把 8 顆感測器觀測送進模型，讓模型校正 `ac_main` 的有效功率與空間 residual；接著固定目標為 25°C／58% RH／500 lux，只比較 AC activation 35%、60%、85% 三個候選。模型預測的 zone temperature 分別是 27.509°C、26.559°C、25.609°C，comfort penalty 分別是 3.898、2.907、2.308，因此這次 dry run 排名第一的是 85%。真正介入時，才把 85% 送到 actuator，再用介入後實測溫度和 25.609°C 比較 MAE；這一步目前尚未有實體證據。
機箱模型版示範（示範計算，不是實測）：我把狀態固定為入口 30°C、CPU 72°C、負載功率 180 W，並先用一組待 calibration 的參數 C=12000 J/°C、G=8 W/°C、k_f=1.5 W/(°C·krpm)、5 分鐘 horizon。假設 PWM 40%／60%／80% 分別對應 3000／4500／6000 RPM，模型計算出的 5 分鐘後 CPU 溫度示範值為 63.38／61.01／58.65°C。這個例子展示的是「候選風扇操作 → 預測後續溫度」的格式；真正研究時，這些係數要由 calibration 資料辨識，再用 validation／holdout 的實測溫度計算 MAE。

機箱模型版本：每個參數能調什麼、代表什麼

因為教授目前把機箱視為主軸，我把同一套調適方法改寫成機箱模型的參數表。這週先把內容分成三類：模型中的控制輸入、要用 calibration 辨識的熱模型參數，以及不能為了分數事後改動的安全／實驗參數；這不是在宣稱我已經有一台可介入的實體機箱。

參數類型改變後的效果意義
PWM操作改變風量、降溫速度與風扇功耗真正送給風扇的控制動作
RPM觀測回應反映命令是否真的變成轉速不能把 PWM 直接當成 RPM

完整機箱參數調適 protocol：enclosure parameter adaptation protocol。目前是本週完成的方法設計；BMC 資料尚無可重設 PWM 介入，不把它寫成已完成的機箱控制結果。

我接著嘗試建立 holdout，已恢復 pinned FMU 與 FMPy 0.3.22；但實際執行 day 270 時發現 FMU 只有 Linux x86-64 的 shared library，沒有 macOS ARM 可載入的 library，所以在第一個 transition 前停止。我把這次記為 PILOT_BLOCKED，沒有補造數字或重跑 E15。

為了確認 protocol 和 gate 本身沒有邏輯漏洞，我另外跑了一個 deterministic toy dynamic API。它完整通過 calibration／validation／holdout 與 hash 檢查，但我把它標成 PASS_CONTRACT_TEST_NOT_RESEARCH_EVIDENCE，不把 toy 結果當成 BOPTEST 或實體設備結果。

在 BOPTEST binary 受平台限制後，我改用第二候選 TCLab。`tclab==1.0.0` 的 `TCLabModel(synced=False)` 已跑通 reset、輸入 Q1/Q2、時間推進與 T1/T2 回應；固定 seed 下 holdout 重跑 hash 一致。這是 simulation pilot 通過，但不是 TCLab 硬體、BOPTEST 或真實介入證據。

後來我用 GitHub Ubuntu runner 恢復 BOPTEST 的 Linux x86-64 runtime，跑了預先鎖定參數的 day 240 validation 與 day 270 holdout，並在相同日期跑 fixed PI baseline。結果如下：

我另外從兩條 locked trace 各隨機抽取最多 100 個狀態，在系統已選出的操作下，用既有 development calibration 固定的一階 RC predictor 預測下一步溫度，再和實際 `next_T` 比較。200 個抽樣的 MAE 為 1.6073°C、RMSE 為 1.6568°C，沒有樣本落在 0.5°C 內；這表示目前 frozen predictor 還不夠準，不能把操作後溫度結果寫成已被準確預測。

因此我的 gate decision 是：我先不進入真實裝置介入。這兩個日期支持我繼續做多 testcase／多 seed 的獨立確認，但還不足以把 E8 寫成已完成；E8 仍是 NOT_EVALUATED。
