# 2026-09-21 本週研究進度口頭講稿

## 報告定位

這份講稿是配合 `professor_catchup_report_2026-09-21_zh.html` 的口頭版本，預計約 12–15 分鐘。這週的應用主軸只談桌機機箱模型與控制驗證；GRU／LSTM、E15 與前一輪公開資料結果只作為研究背景，不宣稱為本週新實驗。

## 開場：這週我完成了什麼（約 1 分鐘）

老師好，這週我把研究往「模型預測出的操作，實際上會不會帶來預期的溫度結果」這個問題推進。

我完成三件事。第一，我把參數調教整理成一個可以重複的流程，明確區分 calibration、validation 和 holdout。第二，我跑通了 TCLab 的本地模型 API，確認 reset、控制輸入和溫度回應可以被重現。第三，我在 Linux runner 上完成 BOPTEST 的 locked／holdout 控制驗證，並另外抽樣檢查選定操作之後的溫度預測準確度。

這週我也把應用方向收斂到桌機機箱。木材、線材與溫濕度不再是目前研究主軸；機箱的入口溫度、CPU／GPU 溫度、負載功率、PWM 與 RPM 才是後續資料契約的核心。

## 研究問題：我現在要回答什麼（約 1 分鐘）

我現在不是只問模型能不能估計一個溫度，而是分成兩個連續問題。

第一，在已知目前狀態和負載的情況下，模型能不能預測不同風扇操作後的溫度？第二，在相同負載與安全限制下，模型選出的 PWM 或 RPM 操作，是否比固定轉速或原廠策略更能避免超溫，同時不增加不必要的功耗？

這兩個問題要分開驗證。預測誤差變小，不等於控制一定有效；沒有可重設的介入，就不能把觀測到的 BMC trace 寫成真實控制效果。

## 前一輪成果只作背景（約 1 分鐘）

前一輪我曾經比較 Pure RNN、GRU 和 LSTM。在固定設定下，這些較複雜的模型沒有取得最低 MAE，所以我目前不把增加模型複雜度當成自然的改進方向。E15 則是在固定模型後，用另外 14 個先前未開啟的檔案、3,112 筆資料做確認；MAE 從 1.6939 降到 0.9744°C，12/14 runs 改善，十項門檻通過。

不過 E15 的範圍只到同一台 Phytium S2500 伺服器的時間與工作負載轉移，不能直接推成桌機機箱、跨伺服器或真實控制證據。因此這些結果是我這週選擇研究方向時的背景，不是本週新增的機箱實驗。

## 我遇到的問題，以及我怎麼找 API／模擬平台（約 2 分鐘）

當我想驗證操作後的溫度時，我遇到三個限制。第一，現有資料多半是觀測資料，沒有可重設的 PWM 介入。第二，我需要同時看到量測、送出操作，再觀察系統往前演化，單純靜態資料集不夠。第三，我必須知道預測誤差和控制效益是不是被同一個資料切分公平地比較。

因此我查了四類候選：TCLab 的本地熱模型、BOPTEST 的控制模擬環境、UCI SECOM 資料，以及 OpenHumidistat 的研究資料。它們的角色不一樣：TCLab 和 BOPTEST 是可推進時間與送出控制輸入的模擬環境；SECOM 是靜態製程資料；OpenHumidistat 是另一種環境控制研究來源，不能直接當作機箱資料。

BOPTEST 公開服務在當時的連線測試沒有成功，所以我沒有把連線失敗寫成平台永久不可用；我先固定官方 v0.9.0 FMU，用 FMPy 在本地讀取量測並送入限制後的控制指令。之後我再用 Linux x86-64 runner 恢復 runtime，完成 locked／holdout run。這代表本地 FMU 與 runner 的驗證已完成，但不等於我已經重現官方服務的全部 KPI 流程。

## 本週的系統性參數調教（約 2 分鐘）

我把參數分成三層。第一層是模型參數，例如熱容量 C、散熱係數 G、風扇增益 k_f、風扇延遲 tau_f，以及負載發熱係數 k_L。這些參數要用 calibration 資料辨識。第二層是控制器參數，例如 PID 的 Kp、Ki、Kd；它們只能在預先固定的搜尋範圍內調整。第三層是安全與實驗設定，例如取樣時間、溫度上限、PWM 變化上限和預測 horizon；這些要在看結果前先固定。

實際流程是：先用 calibration 做辨識與搜尋，鎖定一組參數後，validation 和 holdout 各只讀取一次，再和同日期的 fixed PI baseline 比較。我也預先固定搜尋預算、IAE／ITAE、tie margin 和飽和檢查，避免一直試到分數滿意，或把持平結果硬說成勝出。

### 機箱版每個參數的作用

如果用機箱來說明，我會把每個參數的作用講清楚：

- `PWM` 是送給風扇的控制命令，改變風量、降溫速度與風扇功耗；`RPM` 是實際轉速回應，不能把 PWM 直接當成 RPM，因為它還會受到風扇曲線、負載與延遲影響。
- `Kp`、`Ki`、`Kd` 是 PID 控制器參數。`Kp` 決定看到溫差時反應多強，`Ki` 累積長期誤差以消除穩態偏差，`Kd` 觀察誤差變化以抑制過衝；調整它們會改變反應速度、振盪和穩態誤差。
- `C` 是熱容量，表示 CPU、散熱器與機箱累積熱量的能力，主要影響升溫和降溫的快慢。
- `G` 是自然散熱係數，表示機箱向入口環境散熱的強度；`G` 越大，沒有額外風扇作用時回到入口溫度的速度通常越快。
- `k_f` 是風扇冷卻增益，描述 RPM 或風量增加後能帶來多少散熱，是「操作後溫度」預測的核心係數。
- `τ_f` 是風扇與感測反應的延遲，決定命令送出後多久才看到溫度變化，避免控制器因為太早看不到效果而重複加大 PWM。
- `k_L` 是負載發熱係數，描述 CPU／GPU 功率或負載上升會增加多少熱；它可以讓模型在負載上升前做風扇前饋，減少溫度尖峰。
- `T_warn` 和 `T_limit` 是安全溫度門檻，`ΔPWM_max` 是每一步允許的最大 PWM 變化，`H` 是預測時間範圍。這三類設定用來限制超溫、抖動與評估距離，必須在看結果前固定，不能為了分數事後修改。

所以參數不是全部用同一種方式調整：`C/G/k_f/τ_f/k_L` 由 calibration 辨識，`Kp/Ki/Kd` 在鎖定的模型上搜尋，PWM 是實際候選動作，而安全門檻、取樣時間和 `H` 是事前固定的實驗條件。

我用 DigitalTwinModel 做了一個具體 dry run。狀態固定為入口 30°C、CPU 72°C、負載 180 W，PWM 40%、60%、80% 對應 3000、4500、6000 RPM；模型預測五分鐘後 CPU 溫度分別是 63.38、61.01、58.65°C。模型因此會選 80% PWM。這只是示範「候選操作到預測溫度」的計算格式，還不是實體機箱實測；真正研究時，係數要由 calibration 辨識，再用 holdout 的實測溫度驗證。

## 已選操作後的預測準確度（約 1.5 分鐘）

我另外做了 action-conditioned replay。意思是先依模型規則選出操作，再看這個操作發生後，模型預測的溫度和 trace 中的結果差多少，而不是只拿目前溫度和下一個時間點做 persistence 比較。

在固定的 BOPTEST trace 中，我抽樣 200 個狀態，使用 frozen RC predictor。結果 MAE 是 1.6073°C，RMSE 是 1.6568°C，0% 落在 0.5°C 以內。這個結果對我很重要，因為它說明目前 predictor 還不能被描述成足夠準確；模型雖然可以排序候選操作，但操作後的溫度誤差仍需要改善。

這裡我會特別區分兩件事：模型挑到一個看起來較好的動作，是 action ranking；預測該動作後的溫度是否接近實際值，是 action-conditioned prediction accuracy。前者成立，不代表後者已經成立，更不代表真實機箱控制效益已經成立。

## BOPTEST 的 locked／holdout 結果（約 1 分鐘）

在 Linux runner 上，我用預先鎖定的參數跑 day 240 validation 和 day 270 holdout，也在相同日期跑 fixed PI baseline。兩個日期的 locked PI tracking metrics 都較低，但飽和比例較高。我目前把它解讀為單一 FMU、兩個日期的探索性支持：方法在這個模擬條件下有可比較性，但還不能擴張成跨設備通用或節能的因果結論。

因此目前最誠實的結論是：調參流程和控制評估流程已經跑通，預測操作後溫度的指標也已經產出；但是實體機箱介入、多 testcase、多 seed 和跨設備泛化仍然沒有完成。

## 接下來的機箱研究（約 1 分鐘）

我下一步會先建立機箱資料契約，至少同步入口溫度、CPU／GPU 溫度、負載功率、PWM、RPM 和取樣時間。接著我會用階躍回應辨識 C、G、k_f、tau_f、k_L，再固定 calibration／validation／holdout，比較固定風扇、原廠策略、PID 和模型預測操作。

我會先補多 testcase 和多 seed 的獨立確認，再考慮 E8 intervention。現在 E8 仍是 `NOT_EVALUATED`，我不會把觀測性的 BMC 資料當成已完成的控制實驗。

## 請教授確認的三件事（約 1 分鐘）

第一，我想請老師確認：先以入口溫度、CPU／GPU 溫度、負載功率、PWM、RPM 和取樣時間建立機箱資料契約，是否足以支撐後續控制問題？

第二，目前我只有模擬控制證據，而且跨設備結果同時有改善與失敗。我想請老師決定，控制探索是否應正式納入主論文，還是先把主論文集中在估測與虛擬感測。

第三，我正在比較三個層次：稀疏目標點估測、有限資料參數調適，以及機箱風扇操作後的溫度預測準確度。如果簡單固定策略已經足夠，我也想請老師確認是否仍有必要引入更複雜的控制器。

## 結尾（約 30 秒）

總結來說，這週我完成了系統性參數調教、TCLab 本地模擬、Linux BOPTEST locked／holdout 驗證，也首次把「選定操作之後的溫度預測準確度」單獨量化。200 個抽樣的 MAE 是 1.6073°C，這表示目前模型還需要改善，而不是已經完成控制驗證。接下來我會以桌機機箱為唯一應用主軸，先把資料契約、模型參數辨識和獨立 holdout 做完整，再決定是否進入實體介入。
