# 機箱溫度虛擬感測研究進度報告

**日期：** 2026-08-24  
**建議報告時間：** 8–10 分鐘  
**研究主軸：** 以稀疏 IoT 感測資料推估機箱內關鍵溫度，建立可供空間智慧與決策支援使用的虛擬感測方法。

## 一、今天要回答的問題

目前模型是否已證明能在電腦機箱內準確使用？答案是：**尚未**。現階段已得到公開伺服器 BMC 資料上的候選模型與同資料來源證據，但還沒有桌上型電腦機箱、NTC 實體量測或跨伺服器驗證。今天的主要成果，是把原本不可信的跨 run 實驗修正成可追溯、可重現的研究流程，並得到值得進一步確認的候選模型。

## 二、證據發展過程

### E11H/E11F：同一量測 campaign 的初步正結果

- E11H 開發：模型 MAE/RMSE/P95 為 **0.404/0.683/1.290 °C**。
- E11F 凍結確認：模型為 **0.397/0.672/1.276 °C**，39/42 個序列勝過 baseline。
- 限制：這只支持同一 campaign 內的 unseen bytes，不代表跨機箱或跨硬體泛化。

### E12/E13：跨 run 實驗暴露資料問題

- E12 的每檔至少 30 rows 閘門使 5 個短 run 在開啟最終測試前失敗。
- E13 將門檻依開發資料降為 10 rows，但結果出現數億度等不可能數值。
- 後續證明這不是單純模型失效，而是 InfluxDB 每個 `#group` section 有不同 header；舊解析器把 host counter 對到 BMC 溫度欄位。
- 因此 E13 數值被保留，但標記為 **parser-invalidated**，不能當成模型證據。

### E14A/E14B：先修資料，再談模型

- E14A 改為逐 section 重設 header，只接受 `_measurement=sdgp` 且 `device_id=bmc`。
- 31/31 檔案與獨立 oracle 列數一致，共 4,038 rows，host timestamp 也成功排除。
- 仍發現三個檔案使用毫度 Celsius 與 microwatt，最大 raw CPU temperature 為 59,500。
- E14B 以 section 中位數辨識單位制度，三個檔案套用 `10^-3` 溫度與 `10^-6` 功率縮放，其餘 28 個維持原單位。
- E14B 八個資料品質閘門全部通過；校正後 CPU 溫度為 31–77.5 °C、PSU 總功率為 136–513 W。

## 三、E14C 回溯敏感度結果

在修正後資料上，固定 inlet baseline 與 load-aware ridge model：

| 指標 | Baseline | Ridge | 改善 |
|---|---:|---:|---:|
| MAE | 4.088 °C | 1.805 °C | 2.283 °C |
| RMSE | 5.209 °C | 2.800 °C | 2.409 °C |
| P95 | 12.000 °C | 7.115 °C | 4.885 °C |

- 測試資料：14 runs、3,242 rows。
- Ridge 在 **13/14 runs** 勝過 baseline。
- run-block bootstrap 的 macro MAE gain 95% CI 為 **[1.427, 2.794] °C**。
- 預測範圍為 **37.00–64.36 °C**，未出現不合理外插。

解讀：候選方法在修正後資料上表現明顯較好，**有資格進入新的凍結確認**。但 E14C 的測試 bytes 在解析器除錯時已被開啟，所以只能稱為 retrospective sensitivity analysis，不能宣稱獨立確認成功。

## GRU 與 LSTM 簡易版結果

這週另外把先前登錄的 GRU 與 LSTM 各做了一個簡易版。兩者和 vanilla RNN 使用相同 SML2010 資料、四筆歷史、70/30 時序切分、12 個測試案例、30 epochs 與 seed 42；為避免模型大小不公平，三者參數量控制在 148、169、140。

結果是 GRU 和 LSTM 都沒有在任何一個案例拿到最低 MAE。GRU 只在兩個 60 分鐘濕度案例勝過 vanilla RNN，整體為 2/12，其中位相對 MAE 改善為 -12.88%；LSTM 為 0/12，中位相對改善為 -11.37%。因此原本設定的「至少 8/12 勝出且中位改善為正」沒有通過，這次不把任何模型送進完整 3D 比較。PID 仍未執行。

## 四、目前可以與不可以宣稱的內容

**可以宣稱：**

- 已建立 section-aware、source-aware、unit-aware 的 BMC 資料管線。
- 已找出 load-aware ridge 作為有潛力的低複雜度虛擬溫度感測器。
- 在 E14C 回溯分析中，候選模型的平均、尾端與跨 run 指標均優於 inlet baseline。

**不可以宣稱：**

- 尚未證明模型可直接用於桌上型電腦機箱。
- 尚未證明跨伺服器、跨感測器或跨環境泛化。
- 尚未以 NTC 實體硬體驗證，也沒有空間溫度場真值。
- 尚不能把 BMC CPU 溫度推估等同於整個房間或機箱的數位分身。

## 五、NTC 是否適合作為後續測溫硬體

NTC 可以作為低成本測試感測器，但必須搭配已校正參考溫度計、精密分壓電阻、穩定 ADC、Beta 或 Steinhart–Hart 轉換，以及固定安裝位置。主要誤差來源包括個體容差、自熱、導線電阻、ADC 參考電壓、熱慣性與接觸方式。建議後續先做冰水點、室溫與約 50–70 °C 的多點校正，再進入機箱；依目前研究安排，本輪暫不執行實體測試。

## 六、本週研究方向上的重大難題

### 1. 公開伺服器資料是否偏離「電腦機箱」研究主題

目前資料來自 Phytium S2500 伺服器 BMC，target 是雙 CPU socket 的較高溫度；它不是桌上型電腦機箱的空間溫度場。若直接把結果寫成「已驗證機箱模型」，研究主張會超過證據。

**解法：** 把研究拆成證據階梯。第一階段用公開 BMC 驗證虛擬感測方法與跨工作負載穩定性；第二階段才以 NTC 建立桌機多點溫度真值；第三階段再整合房間座標、zone 與非聯網設備影響。現階段只停在第一階段。

### 2. 模型表現好，是否等於能跨環境使用

E11F 在同一 campaign 表現很好，但同 campaign 的 unseen bytes 主要證明內插能力，不能回答跨日期、風扇策略或 workload 是否仍有效。

**解法：** 將驗證單位改成完整 run，使用時間與 workload 分離，模型在確認前凍結。E14C 只負責找出候選模型；E15 才用較晚的 TEAP、kernel、synthetic 與 Jenkins runs 檢驗同伺服器的時間外推。即使 E15 通過，仍不宣稱跨伺服器或跨機箱。

### 3. 論文真正要預測的「溫度」是什麼

目前 `target=max(Cpu1_Temp, Cpu2_Temp)` 代表伺服器熱點代理值，不是機箱進風、出風、GPU、硬碟區或房間 zone 的完整溫度場。若 target 沒有分層，後續 NTC 與空間智慧會和現有模型無法對接。

**解法：** 明確區分三種 target：目前的元件熱點虛擬感測、後續機箱 zone 溫度，以及最終房間空間溫度與設備影響。每一層使用不同真值、座標與誤差指標，不把 CPU hotspot 當成整個數位分身。

### 4. 應該追求複雜模型，還是先追求可確認性

有效獨立 runs 數量有限，直接使用 LSTM 或大型非線性模型容易把時間相關性與控制策略記住，也難判斷改善來自模型還是資料洩漏。

**解法：** 先用 inlet-plus-offset 作為可解釋 baseline，以低維 load-aware ridge 建立最低可行候選。評估同時看 MAE、RMSE、P95、逐 run 勝率與 run-block bootstrap。只有新資料確認後，才考慮 Huber、selective regression、OOD abstention 或 conformal interval，而不是先增加模型容量。

### 5. IoTaIS 論文的新穎性應放在哪裡

單純做 CPU 溫度 regression 很難形成完整研究貢獻；若把 MCP 當成主要 novelty，又會偏離 IoT sensing 與 intelligence systems 的核心。

**解法：** 將論文主軸定為「稀疏 IoT 感測下的室內空間智慧」：由少量感測點學習非聯網設備的熱影響，產生虛擬感測與決策支援。BMC 實驗是方法驗證的一部分，MCP 僅是讓服務被查詢的次要介面。後續必須以座標化 NTC 機箱/房間資料補上最終 domain evidence。

Parser、單位、下載與建置環境等問題仍完整保留在 `docs/research/research_difficulty_log_zh.md`，但只作為技術執行紀錄，不再當作本週研究方向的主要難題。

## 七、下一步：E15 真正的凍結確認

E15 已在讀取結果前完成預註冊：固定 E14C 模型 SHA-256、固定 14 個 2023-08 至 2024-05 runs、固定 10 個資料與準確度閘門，涵蓋 For-And-Join、TEAP、kernel、synthetic 與 Jenkins。模型不重訓、不重新選特徵，也不因結果替換檔案。

下一個明確動作是取得下載授權後執行一次 E15。若全部閘門通過，只能支持「同一伺服器資料庫內的跨時間與工作負載確認」；若失敗，將逐 run 判斷是資料品質、控制策略 drift，還是模型泛化不足。

## 八、結論講法

> 今天不是證明模型已經能放進電腦機箱，而是完成了更重要的研究工作：找出錯誤資料管線、建立單位與來源驗證、保留失敗結果，並將候選模型推進到可接受真正新資料檢驗的階段。E14C 顯示模型有潛力，E15 才是下一個確認關卡。

## 老師可能追問

**為什麼不用更複雜的深度學習？** 目前有效 runs 數量有限，跨 run 漂移比模型容量更關鍵；ridge 可凍結、可解釋，也較容易定位資料錯誤。

**為什麼 bootstrap 以 run 為單位？** 同一 run 的時間點高度相關，逐 row 重抽會把樣本量誇大；run-block bootstrap 對跨實驗泛化更保守。

**E14C 這麼好，為什麼還不能算驗證？** 因為測試 bytes 已參與 parser 除錯。即使沒有用標籤調參，獨立性仍受損，所以主動降低為回溯敏感度證據。

**這和 IoT/空間智慧的關係是什麼？** BMC 實驗先驗證低成本稀疏感測加虛擬感測的核心方法；後續才把感測點、機箱區域與房間座標整合成決策支援服務。
